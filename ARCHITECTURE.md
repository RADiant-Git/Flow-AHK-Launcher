# Архитектура FlowKey Manager

Документ описывает целевую архитектуру, принципы и модель взаимодействия
с пользователем. Раздел «Проблемы предыдущей реализации» объясняет, почему
рефакторинг нужен; раздел «Слои» — как устроено сейчас.

---

## 1. Что это за система и её главное ограничение

Плагин Flow Launcher, который переназначает клавиши и кнопки мыши, транслируя
правила в скрипт AutoHotkey v2.

Ключевое ограничение, из которого вытекает весь дизайн:

> **Flow Launcher запускает Python-плагин как отдельный процесс на каждое
> взаимодействие.** keystroke в строке поиска → новый процесс; нажатие Enter →
> новый процесс. Между вызовами общая память отсутствует.

Отсюда три следствия:

1. Плагин **не может хранить состояние в себе** — всё состояние живёт на диске
   и должно быть читаемым за один проход.
2. **Каждый вызов должен быть быстрым.** Блокирующий захват нажатием —
   исключение, которое надо оформлять как отдельный явный шаг, а не встраивать
   в обычный `query`.
3. **Два процесса могут написать один и тот же файл.** Чтение-модификация-запись
   обязаны быть атомарными и защищёнными.

Второй по важности источник багов: **состояние мастера выдавалось через текст в
строке поиска** (`key target: `, `key app: `, `key error: `). Строка поиска —
поле, которое пользователь редактирует свободно, поэтому оно не может быть
источником правды. Отсюда дыра: напечатать `key target: esc` вручную, не записав
триггер, — и плагин сгенерирует заведомо битый скрипт.

## 2. Проблемы предыдущей реализации

| # | Проблема | Род |
|---|---|---|
| 1 | `main.py` = 660 строк: HTTP-подобный роутинг, бизнес-логика, презентация и генерация AHK в одном классе | смешение слоёв |
| 2 | `context_menu(data)` принимал `data` за строку; хост V1 передаёт **список** (или `ContextData`) → меню не появлялся | неверно понятая граница протокола |
| 3 | Неизвестный метод → `KeyError` внутри базового `flowlauncher`, процесс падает, Flow Launcher молча ничего не показывает | отсутствие границы |
| 4 | Два независимых пути создания правила (`parser.parse → apply_dsl_string` и `capture → session → finish_rule`) с одинаковой формой записи, но разной семантикой полей; `hold` в одном — флаг, в другом — префикс `!` | дублирование |
| 5 | Конфликт триггеров обнаруживался только при генерации скрипта, то есть **после** сохранения правила. Пользователь получал «молча не работающее» правило | валидация не в модели |
| 6 | Состояние мастера в строке поиска | источник правды |
| 7 | `save_modules` — обычный `open("w")`: обрыв записи уничтожает все правила; параллельные процессы теряют обновления | отсутствие атомарности |
| 8 | Нет способа узнать, что запущенные хуки соответствуют `modules.json` | нет концепции применения |
| 9 | Захват нельзя отменить; Esc становится триггером; ввод заблокирован на весь таймаут | модель взаимодействия |
| 10 | Каталог не различает, годится ли клавиша как триггер, как цель `Send` или как цель ремапа: `LCtrl` предлагались в цели (бесполезно), колесо — в триггеры | модель данных |
| 11 | `IcoPath` продублирован в `plugin.json` и `main.py` (отсюда уже рождался баг со сломанной иконкой) | дублирование |

## 3. Целевые принципы

1. **Единственный источник правды — доменная модель** (`RuleSet` в `modules.json`,
   формат v2). Всё остальное — производное: `runtime.ahk` функция от модели,
   строка поиска — только навигационное намерение.
2. **Валидация в модели, а не в генераторе.** Непустое/некорректное значение
   отклоняется на входе в `Rule`, до записи на диск. Конфликт триггеров —
   ошибка добавления, а не предупреждение при codegen.
3. **Чистая кодогенерация.** `ahk.codegen.render(ruleset) -> text` — чистая
   функция без побочных эффектов и без доступа к диску: её можно тестировать без
   AutoHotkey.
4. **Граница протокола изолирована.** `core/rpc.py` единственный модуль, который
   знает про форму argv. Он нормализует вход (`query` строкой или словарём,
   `ContextData` списком) и **никогда** не даёт процессу упасть: ошибка
   превращается в карточку результата.
5. **Один конвейер создания правила.** Любой источник — DSL, физический захват,
   выбор из каталога — даёт `RuleDraft`, который проходит один и тот же путь
   `draft → Rule → проверка конфликта → сохранение → применение`.
6. **Атомарность и версионирование данных.** Запись через временный файл +
   `os.replace`, блокировка `msvcrt`, поле `format_version` и миграция.
7. **Применение — отдельное понятие.** Хранится хэш успешно запущенного скрипта;
   расхождение модели и запущенных хуков видимо и лечится одним действием.
8. **Никаких фоновых процессов без нужды.** Пустой набор правил не должен держать
   резидентный AHK-процесс с глобальным клавиатурным хуком.
9. **Пользователь всегда знает, что происходит и как выйти.** Отмена на каждом
   шаге, явные формулировки отказов, причина отказа рядом со следствием.

## 4. Слои

Зависимости направлены строго вниз. Верхние слои ничего не знают о нижних
реализациях, только об интерфейсах.

```
                 Flow Launcher  (процесс на каждый вызов)
                          │ argv: JSON
        ┌─────────────────▼─────────────────┐
        │ core/rpc.py        ГРАНИЦА       │  нормализация входа, диспетчер,
        │                                    │  «не упасть ни при каких условиях»
        └─────────────────┬─────────────────┘
        ┌─────────────────▼─────────────────┐
        │ core/views.py      ПРЕЗЕНТАЦИЯ   │  состояние → карточки результатов
        └─────────────────┬─────────────────┘
        ┌─────────────────▼─────────────────┐
        │ core/services.py   ПРИМЕНЕНИЕ    │  сценарии: создать, переключить,
        │                                    │  удалить, пауза, применить хуки
        └───────┬──────────────────┬────────┘
        ┌───────▼────────┐  ┌──────▼───────────┐
        │ core/model.py  │  │ core/session.py  │   ДОМЕН: правила и мастер
        │ Rule/RuleSet/  │  │ stages, draft    │
        │ конфликты      │  └──────┬───────────┘
        └───────┬────────┘         │
        ┌───────▼──────────────────▼─────────┐
        │ адаптеры: dsl, storage, ahk/*      │  внешний мир: текст, диск, процесс
        └────────────────────────────────────┘
```

### Каталог файлов

| Файл | Слой | Ответственность |
|---|---|---|
| `main.py` | вход | `sys.path` + разовая миграция данных + запуск диспетчера |
| `core/config.py` | вход | Пути (включая выбор каталога данных), `IcoPath` и ключевое слово из `plugin.json`, таймауты |
| `core/rpc.py` | граница | Разбор argv, нормализация, таблица методов, защита от падений |
| `core/views.py` | презентация | Как выглядит каждый экран |
| `core/services.py` | применение | Сценарии-транзакции: прочитал → изменил → сохранил → применил |
| `core/model.py` | домен | `Rule`, `RuleDraft`, `RuleSet`, доменные ошибки, конфликты |
| `core/session.py` | домен | Машина состояний мастера + нормализаторы намерений из строки поиска |
| `core/catalog.py` | домен | Клавиши: имена, алиасы, **роли** (trigger / send / remap) |
| `core/dsl.py` | адаптер | Текст формулы → `RuleDraft` (чистая функция) |
| `core/storage.py` | адаптер | Атомарный JSON с блокировкой и миграцией формата |
| `core/ahk/codegen.py` | адаптер | `RuleSet` → текст `runtime.ahk` (чистая функция) |
| `core/ahk/runtime.py` | адаптер | Поиск AHK, `/validate`, запуск/вытеснение, автозапуск, хэш применения |
| `core/ahk/capture.py` | адаптер | Захват нажатия: таймаут, отмена, разбор ответа |
| `tests/` | — | Домен, DSL, кодогенерация, захват, хранилище, граница RPC, мастер |

Заменены: `core/parser.py` → `core/dsl.py`,
`core/ahk_engine.py` → `core/ahk/*`. Имя `modules.json` сохранена, чтобы не
ломать существующие установки и привычку пользователя.

## 5. Модель данных

### Rule

```python
Rule(
    id: str,              # короткая метка, только для перемещения по UI
    name: str,            # человекочитаемое имя (выводимое, не источник правды)
    trigger: str,         # AHK-спецификатор без префикса "*": "^e", "w", "MButton"
    action: str,          # имя клавиши ИЛИ готовая Send-последовательность
    scope: str,           # "*" (везде) или имя процесса ("Code.exe")
    mode: "send"|"remap", # send = Send('...'), remap = нативный ремап AHK
    enabled: bool,
    transparent: bool,    # ~ : исходное нажатие не съедается, уходит и в окно
)
```

`mode` пришёл на смену булеву `hold`: `hold` = «удерживать», а реальная разница —
в способе выражения действия. `format_version: 2`; при чтении версии 1 выполняется
миграция (`trigger_ahk→trigger`, `target→action`, `app→scope`,
`hold→mode`, `trigger_human` сохраняется как `human` для подписи).

`transparent` — единственное поле, влияющее на **префикс** хоткея (`~*trig::`), а
не на его тело. Оно запрещено вместе с `mode="remap"` на уровне модели: ремап сам
превращает исходную клавишу в целевую, пропускать ему нечего. Поле
дополнительное: у записей, где его нет, читается `False`, поэтому поведение уже
созданных правил не меняется.

### Конфликт

`(scope.lower(), trigger.lower())` — уникальный ключ внутри `RuleSet`.
`RuleSet.add()` бросает `DuplicateTrigger`, содержащий имя занявшего правила.
Так отказ происходит **до** записи на диск и формулируется человеческим языком.

### Роли клавиш

Клавиша годна в разные слоты по-разному:

| Клавиша | Триггер | Цель `send` | Цель `remap` | Почему |
|---|---|---|---|---|
| `w`, `Escape`, `F5` | да | да | да | |
| `LCtrl`, `LAlt` | да | **нет** | да | одиночное `{LCtrl}` в Send — нажать и отпустить, эффект нулевой; в ремапе осмысленно |
| `WheelUp` | **нет** | да | нет | InputHook колесо не ловит как end-key |
| `LButton`, `MButton` | да | да | **нет** | AHK не поддерживает ремап мышь→мышь и клавиша→мышь |

Каталог возвращает кандидатов по роли, поэтому в меню выбора действия больше не
появляются модификаторы, а в триггеры — клавиши колеса.

### Где лежат данные

`modules.json`, `session.json` и сгенерированный `runtime.ahk` лежат **вне папки
плагина** — в каталоге настроек плагина Flow Launcher
(`%APPDATA%\FlowLauncher\Settings\Plugins\<Name>` или
`<папка программы>\UserData\Settings\Plugins\<Name>` в портативной установке).

Причина не косметическая. Flow Launcher обновляет плагин так: распаковывает новую
версию в соседнюю папку (`<Name>-<Version>`), а старую помечает файлом
`NeedDelete.txt` и удаляет при следующем запуске. Всё, что лежит внутри папки
плагина, обновление уничтожает; каталог настроек не трогается ни при обновлении,
ни при удалении плагина с сохранением настроек. Пока данные жили рядом с кодом,
первый же апдейт из магазина стирал пользователю все правила.

`core/config.py` воспроизводит формулу пути из `DataLocation.cs` самого Flow
Launcher (портативный режим главнее, но только если каталог `UserData`
существует и не помечен файлом `.dead`). Разбор путей — чистые функции,
поэтому проверяются тестом без запуска Flow Launcher; миграция старых установок
выполняется из `main.py`, а не при импорте модуля, чтобы импорт не писал на диск.

## 6. Граница RPC

Единственное место, знающее о форме argv. Три нормализации, каждая из которых
раньше была источником отдельного бага:

1. **Неизвестный метод** → не `KeyError`, а пустой результат. Падение процесса
   для Flow Launcher неотличимо от «ничего не найдено».
2. **`context_menu`** → аргумент всегда **список** (параметры `JsonRPCAction`
   выбранной карточки либо `ContextData`). Извлечение id — `data[0]` после
   проверки типа, а не сравнение со строкой.
3. **`query`** → строка или (в новых хостах) словарь `{"search": ...}`;
   используется только `search`, потому что `rawQuery`/`trimmedQuery` содержат
   ключевое слово `key` и при наивном использовании ломают разбор.

Обработчики описаны таблицей `name → (функция, ожидаемая сигнатура)`, а не
`inspect.getmembers`, поэтому опечатка в имени метода видна сразу в тестах.

**Любое** исключение внутри обработчика превращается в одну карточку
«⚠️ Ошибка плагина» с текстом проблемы: плагин никогда не оставляет пользователя
с молча пустым списком.

## 7. Модель взаимодействия с пользователем

### Экран = состояние, а не текст в строке поиска

Мастер — явная машина состояний в `session.json`:

```
IDLE ──записать триггер──► AWAIT_ACTION ──действие──► (сохранение) ──► IDLE
  │                            │
  │                            └── изменить окно ──► AWAIT_SCOPE ──► AWAIT_ACTION
  └── DSL-формула ────────────────────────────────► (сохранение) ──► IDLE
```

Префиксы `new`, `target:`, `app:` остаются, но трактуются как **навигационное
намерение**, а не как состояние. Каждый экран сначала спрашивает у мастера
`draft()`: если состояние не соответствует, экран не рендерится в пустоту, а
возвращает карточку «Сначала запишите клавишу-триггер» с переходом к нужному
шагу. Это закрывает дыру №6.

### Правила взаимодействия

1. **Enter — всегда главное, единственное действие строки.** Вторичные действия
   (выключить, удалить, ограничить окном) — в контекстном меню (`Ctrl+O` / ПКМ).
2. **Подпись строки объясняет, что сделает Enter**, и не обещает того, чего нет.
3. **Отказ с причиной.** Правило не применено → карточка «⚠️» вверху с текстом
   причины и способом убрать. Причина формулируется по-человечески:
   не `Invalid key name`, а `Триггер ещё не записан`.
4. **Отмена на каждом шаге.** Захват прерывается по `Escape` (одиночному) и по
   таймауту. Привязать сам `Escape` можно через каталог или DSL — это осознанный
   размен, он описан в справке.
5. **Обратная связь о хуках.** Плагин хранит хэш применённого скрипта; если
   `runtime.ahk` пересобран, но не применён (или хуки убиты извне), это видно.
6. **Ничего не молчит.** После любого изменения — короткое резюме: что создано,
   что пропущено и почему.
7. **Владение нажатием — выбор пользователя, а не следствие реализации.**
   По умолчанию правило забирает исходное нажатие (переназначение и штатная
   функция клавиши — взаимоисключающие). `transparent` переключает это на
   пропуск: срабатывает и переназначение, и то, что делает клавиша сама по себе.
   Выбор живёт в правиле, потому что у разных клавиш разная цена потери
   штатного поведения: для мультимедийной терять нечего, для `XButton1` — есть.

### Что осталось неизмеренным

Проверено экспериментально: синтетические нажатия из одного AHK-процесса
активируют хоткеи другого (то есть результат переназначения другие скрипты
ловят), и что `AHK /validate` разбирает скрипт, не выполняя его.

Не проверено: увидит ли другой AHK-скрипт **исходную** клавишу, когда наше
правило её уже перехватило, и меняет ли это `~`. Три попытки измерить дали
противоречивый результат (скрипт-перехватчик не срабатывал даже в одиночестве,
где почти идентичная конфигурация работала), то есть баг был в измерителе.
UI-подписи и документы поэтому формулируют `~` строго как «пропуск в активное
окно» — то, что описано в документации AutoHotkey, — и не обещают ничего про
соседние скрипты.

### Жизненный цикл захвата

```
пользователь жмёт «🎯 Записать»
   → rpc.listen_trigger
      → ahk.capture.run(timeout)          # отдельный AHK-процесс, блокирует ввод
         ├ Escape (без модификаторов) → Cancelled → возврат в IDLE, ничего не создано
         ├ таймаут                     → Timeout  → карточка с кнопкой повтора
         ├ клавиша/сочетание           → Draft(trigger, human)
         └ кнопка мыши                 → Draft(trigger)
      → session.set(AWAIT_ACTION, draft)
         → views.action_step   # новый процесс, состояние прочитано с диска
```

### Жизненный цикл хуков

```
изменение модели
  → ahk.codegen.render(ruleset, paused)      чистая функция, текст
  → ahk.runtime.validate(text)               AHK /validate: разбор без выполнения
      ├ ошибка → модель НЕ помечается применённой, причина в UI
      └ ок     → запись runtime.ahk → запуск (SingleInstance вытесняет старый)
                → сохранение applied_hash
пустой RuleSet → хуки не ставятся, резидентного процесса не остаётся
```

## 8. Тестуемость

Рефакторинг делает проверяемым то, что раньше проверялось только руками:

- `model` — конфликты, валидация триггера/действия, миграция v1→v2;
- `dsl` — формулы, `@scope`, `!`-удержание, отказ на мусоре;
- `codegen` — точный текст скрипта, скобки вокруг имён клавиш, экранирование,
  `#HotIf`-блоки, отсутствие хуков при пустом наборе;
- `capture` — подстановка таймаута в шаблон (шаблон со скобками AHK несовместим
  с `str.format` — на этом прежняя генерация и падала), отмена, разбор вывода;
- `rpc` — формы argv, включая `context_menu` со списком и неизвестный метод;
- `storage` — атомарность, откат транзакции при ошибке, переносимости BOM;
- `session` — переходы мастера и отказ экрана при несовпадении состояния.

`ahk.codegen` и `core.model` не импортируют ни `subprocess`, ни AutoHotkey,
поэтому тесты домена и генерации идут без установленного AHK.
